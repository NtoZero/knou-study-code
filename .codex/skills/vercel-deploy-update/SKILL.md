# Vercel Deploy Update

Use this project skill to turn the current worktree into a verified Vercel deployment while avoiding accidental secret uploads.

## Operating Rules

- Treat "latest", "refresh", "update deployment", "prod", "production", "live", or Korean equivalents like "최신화", "배포", "운영 반영" as permission to deploy the current worktree to production unless the user says preview only.
- If the user only asks whether deployment is safe, stop after the preflight assessment.
- Prefer Vercel CLI over dashboard instructions once the user asks for CLI deployment.
- Use current official Vercel docs through Context7 when command behavior, plan rules, or CLI options matter.
- Do not commit changes unless the user explicitly asks.
- Do not print secret values. If a possible secret is found, report the file path and line number only, then stop before deploying.

## Preflight

Run these checks before any deploy:

```bash
git status --short
git ls-files .env .env.local .env.production .env.development .vercel
rg --files -uu -g '.env*' -g '.vercel/**'
rg -n "API_KEY|SECRET|TOKEN|PASSWORD|PRIVATE_KEY|DATABASE_URL|AUTH_SECRET|BEGIN PRIVATE KEY|ghp_[A-Za-z0-9]{20,}|sk-[A-Za-z0-9_-]{20,}" -S --glob '!package-lock.json' --glob '!node_modules/**' --glob '!.next/**' .
```

Interpretation:

- Dirty worktrees are acceptable for CLI deploys if the user asked to deploy the current local project. Make clear that uncommitted changes are included.
- Existing `.env*` files are not automatically fatal, but verify they are ignored and not uploaded.
- `README.md` examples of secret scan commands are false positives.
- Known non-secret text can be ignored only after reading the matched line.

Ensure source-upload exclusions exist:

```text
.gitignore:     .env, .env.*, .vercel/, node_modules/, .next/, out/, build/, dist/
.vercelignore:  .env, .env.*, .vercel/, node_modules/, .next/, out/, build/, dist/, .git/, .codex/
```

If `.vercelignore` is missing, add it before deploying. Vercel CLI has default ignores, but an explicit `.vercelignore` prevents surprises for files such as `.env.production`.

Run the project build:

```bash
npm run build
```

Shortcut: run `bash .codex/skills/vercel-deploy-update/scripts/preflight.sh` from the project root.

## CLI Setup

Check the CLI:

```bash
vercel --version
```

If missing, install it only after approval because it requires network/global writes:

```bash
npm i -g vercel
```

Check login:

```bash
vercel whoami
```

If the CLI starts a device login flow, give the user the exact URL/code and wait. After login, run `vercel whoami` again.

Link the project if `.vercel/project.json` does not exist:

```bash
vercel link --yes
```

If GitHub repository linking fails due to missing Vercel/GitHub connection, continue with CLI deployment unless the user specifically requested Git-based auto-deploy.

## Deploy

Preview deployment:

```bash
vercel deploy --yes
```

Production deployment:

```bash
vercel deploy --prod --yes
```

Capture the deployment URL, inspector URL, deployment id, target, and ready state from CLI output.

## Verify

After deployment, verify readiness:

```bash
vercel inspect <deployment-url>
```

Verify public HTTP response:

```bash
curl -I <production-or-alias-url>
```

For Vercel protected previews, `vercel curl / --deployment <deployment-url>` can verify through deployment protection, but do not treat generated bypass-token messages as public accessibility proof. Use `curl -I` on the public alias when confirming a live production URL.

## Final Response

Report:

- whether the repo was safe to deploy and what changed for safety, if anything
- local build result and Vercel build result
- deployment target and URL
- verification result, including HTTP status
- any remaining follow-up such as GitHub Login Connection setup for automatic Git deployments
